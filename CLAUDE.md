# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`vertice-bff` is a Backend-for-Frontend: a Fastify HTTP/JSON API that sits between `vertice-web-react` (frontend) and `vertice-api` (a Spring Boot service exposed only over gRPC on `:9090`). It does not own any data itself — every route handler ultimately calls a gRPC method on `vertice-api` and reshapes the response for the frontend. There is no database, ORM, or ODM in this repo.

Sibling repos (as local checkouts, e.g. `../vertice-api`, `../vertice-web-react`):
1. `vertice-api` — `docker compose up -d` (postgres), then `./gradlew bootRun --args='--spring.profiles.active=local'` (gRPC on `:9090`, auth disabled locally).
2. `vertice-bff` (this repo) — `cp .env.example .env && npm install && npm run dev` (REST on `:3000`).
3. `vertice-web-react` — `npm run dev` (Next.js App Router, pinned to `:5173` via `-p 5173` in its own `dev` script, to avoid colliding with this BFF's default `:3000`). Replaces the old Vue-based `vertice-web`, which is deprecated. It calls this BFF server-side only (`BFF_URL`, see its `src/lib/bff.ts`), proxied through its own `/api/*` routes — the browser never calls this BFF directly, so the web needs no `CORS_ORIGIN` entry. `CORS_ORIGIN` (comma-separated list, default `http://localhost:8081`) exists for browser clients that do call the BFF directly, i.e. `vertice-mobile`'s Expo web build.

## Commands

- `npm run dev` — run with hot reload (tsx watch)
- `npm run dev:docker` — same `tsx watch`, but with polling-based file watching (`CHOKIDAR_USEPOLLING=true`, for Docker Desktop bind mounts where inotify doesn't propagate)
- `npm run build` / `npm start` — compile to `dist/` and run the compiled output
- `npm run typecheck` — `tsc --noEmit`
- `npm run lint` — ESLint (flat config, `eslint.config.js`, typescript-eslint recommended rules)
- `npm run ops:issue-setup-tokens [-- --dry-run]` — one-off: issue a password setup link to every CLIENT, CSV on stdout (`scripts/issue-setup-tokens.ts` → `src/ops/`; see the README's "Operations")
- `npm test` — Vitest (`vitest run`); unit tests live next to the code as `*.test.ts` (e.g. `src/modules/workouts/schemas.test.ts`, `src/grpc/call.test.ts`) and don't spin up gRPC
- `docker build .` / the provided `Dockerfile` — containerized dev, runs `npm run dev:docker`

Node 22 (`.nvmrc`, `engines.node` `>=22 <23`, `node:22-alpine` in the Dockerfile). CI (`.github/workflows/ci.yml`, job `build-and-test`) runs `npm ci`, typecheck, lint, test, build and `npm audit --omit=dev --audit-level=high` on every PR and push to `main`; tests must stay runnable without vertice-api, Postgres or a `.env`.

Single-file / single-test runs use standard Vitest filtering: `npx vitest run src/grpc/call.test.ts` or `npx vitest run -t "name"`.

## Architecture

**Request flow:** `src/server.ts` boots `buildApp()` from `src/app.ts`, which registers (in order) the security headers (`src/plugins/security-headers.ts`: `@fastify/helmet` with an API profile, plus `Cache-Control: no-store` on every `/api/*` response), CORS, the global error handler, the request-context plugin, the rate-limit plugin (global bucket + `app.attemptLimit`), the auth plugin, then every feature module's routes under `/api`. A route that serves the same public, personal-data-free answer to everyone can opt out of `no-store` with `config: { cacheControl: '...' }` (only `GET /api/legal/versions` does, pinned by `CACHEABLE_ROUTES` in `src/test/route-authorization.test.ts`; error responses stay `no-store`). Each module is self-contained:

- `routes.ts` — Fastify route registration, param parsing (`parseId`), auth/role hooks, calls into `service.ts`. Route handlers stay thin: parse → authorize → delegate → return.
- `schemas.ts` — Zod schemas for request bodies, parsed explicitly in route handlers (`schema.parse(req.body)`), not via a Fastify validation hook.
- `service.ts` — business logic, gRPC calls, and response shaping. This is where cross-module composition happens (e.g. `clients/service.ts` pulls from `users`, `training-plans`, and `workout-sessions` services to build a roster view).

Not every module has all three files — `users` has no `routes.ts`/`schemas.ts` of its own (its service wraps `UserService`, including the password RPCs `auth` and `clients` use); `dashboard` has `routes.ts` but no `schemas.ts` (no request body to validate).

**gRPC bridge** (`src/grpc/`):
- `loadProto.ts` loads all `.proto` files under `protos/vertice/**` via `@grpc/proto-loader` into `grpcProto`, a dynamically-shaped object with no static type (hence the `as any` at its export — services are consumed through the concrete clients below, not through this object directly).
- `clients.ts` instantiates one gRPC client per service (`userClient`, `exerciseClient`, `trainingPlanClient`, `workoutClient`, `workoutExerciseClient`, `exerciseSetClient`, `workoutSessionClient`, `workoutFeedbackClient`, `trainerClientClient`) against `grpcTarget` (from `env.VERTICE_API_GRPC_HOST`/`PORT`), using insecure credentials (vertice-api runs without TLS locally).
- `call.ts` exports `grpcCall(client, method, request, options?)` (`options`: `{ metadata?, asService?, anonymous? }`), which promisifies grpc-js's callback API and maps gRPC status codes to `HttpError` subclasses (`NOT_FOUND`→404, `INVALID_ARGUMENT`→400, `FAILED_PRECONDITION`→409 `PRECONDITION_FAILED` (a well-formed request the resource's state forbids — kept apart from 400 so the web can tell "fix the form" from "cannot be edited this way"), `ALREADY_EXISTS`→409 `CONFLICT` `Email or CPF already in use` (one message for both, so public register never says which is taken), `UNAUTHENTICATED`→401 `UNAUTHENTICATED` with the fixed message `Session no longer valid` (clients treat it as logout), `PERMISSION_DENIED`→403, `UNAVAILABLE`→503, `RESOURCE_EXHAUSTED`→413 `TOO_LARGE` (the export bounds), else 502). **Only `INVALID_ARGUMENT` relays vertice-api's text** (its `field: message` validation errors); every other status gets a fixed message (`UPSTREAM_MESSAGES`), so no id, email, CPF or Java exception text reaches a client. `grpcCall` logs the upstream text instead, on the request's logger (`requestContext`'s `log`), with emails and CPFs redacted (`redactUpstreamText`); `UNKNOWN`/`INTERNAL`/... are warnings. Don't relay upstream text for a new status without checking every message vertice-api can put there. Every service function funnels through this. `grpcCall` also attaches the caller's verified bearer token as `authorization: Bearer <token>` gRPC metadata, read from an `AsyncLocalStorage` request context (`src/lib/request-context.ts`, opened per request by `src/plugins/request-context.ts` and filled by `app.authenticate` after verification) — so no service signature carries it. With no verified user token it fails closed (`MissingCallerIdentityError`, nothing goes upstream) unless the call site opts in explicitly: `{ asService: true }` sends the BFF's service token (`serviceToken()` in `src/lib/jwt.ts`) and is refused on any RPC outside `SERVICE_TOKEN_RPCS` (`VerifyCredentials`, `CreateUser`, `SetPasswordWithToken`: login, register, password setup); `{ anonymous: true }` sends nothing and is used only by the `VERIFY_PASSWORDS=false` dev login, which therefore needs vertice-api's `local` profile; it throws `MissingCallerIdentityError` unless `VERIFY_PASSWORDS` is false and `NODE_ENV` is in `DEV_NODE_ENVS`; an `authorization` passed in `{ metadata }` is sent as is (the ops script's `service:ops` token, `src/ops/ops-token.ts`, minted only in the script process). An unverified `Authorization` header is never relayed. The fake upstream in tests (`src/test/fakeUpstream.ts`) enforces the API contract (`API_SERVICE_SUBJECT_RPCS`) and refuses any other call.

`protos/vertice/**` is a synced copy of vertice-api's `src/main/proto/vertice/**` at the commit pinned in `protos/.api-ref`; never edit it by hand. Change the proto in vertice-api, merge, put the merge SHA in `protos/.api-ref`, run `npm run sync:protos` (`-- --check` verifies, CI runs it; `-- --local` uses `../vertice-api`).

To add a new proto (after it exists in vertice-api and the pin is bumped), sync it, add its path to `PROTO_FILES` in `loadProto.ts` and instantiate a client for it in `clients.ts`.

**Auth** (`src/plugins/authenticate.ts`, `src/lib/jwt.ts`): JWTs are signed/verified by the BFF itself (`JWT_SECRET`), and the same token is forwarded to vertice-api, which verifies it with the shared secret — so `JWT_SECRET` must equal vertice-api's (shared dev default `DEV_JWT_SECRET` in `src/config/env.ts`). Unless `NODE_ENV` (trimmed, lower-cased) is unset, `development` or `test`, there is no default and the BFF refuses to start on a missing, whitespace-padded, sub-32-byte or placeholder secret (mirrors vertice-api's `JwtSecretGuard`). Tokens are pinned to HS256 on sign and verify. `app.authenticate` (decorated onto the Fastify instance) verifies the bearer token and sets `req.user: AuthUser {id, role}` — name and email are not in the token; read them from `GET /auth/me` (login/register return them in the response body). `app.requireRole(...roles)` gates by role (`ADMIN` | `TRAINER` | `CLIENT`). **ADMIN has no defined product yet** (no PRD; QUAL-BFF-001, plan item P1-02): it is admitted only on generic routes (`/auth/me` and its self routes, `/auth/password`, `/muscle-groups`, `GET /exercises`, `GET /exercises/:id`); every trainer- or client-scoped route gates on `TRAINER` and/or `CLIENT`, so ADMIN gets a 403 by role before any upstream call. Don't add `ADMIN` to a role list (or an ADMIN bypass to `ownership.ts`) without a PRD for what ADMIN does there; `route-authorization.test.ts` pins the ADMIN route list. vertice-api's own ADMIN bypass is separate and stays. Both are applied as `preHandler` hooks per-module, not globally — `/health`, `/api/legal/versions` and the public `/api/auth/*` routes (login, register, password setup) are intentionally unauthenticated. `POST /auth/login` checks the password through vertice-api's `VerifyCredentials` (one 401 body for wrong password, unknown email or no password yet); `VERIFY_PASSWORDS=false` restores the old email-only login for the rollout window and is refused outside development/test. Trainer-created clients have no password: `POST /clients` returns a single-use setup token (`setup: {token, expiresAt}`) that the client redeems at `POST /auth/password/setup`; upstream `UNAUTHENTICATED` from password RPCs is mapped to a 400 there and in `POST /auth/password`, since clients treat a 401 as logout. Public registration is TRAINER-only.

**Consent (P1-04):** `POST /auth/register` accepts `acceptedTermsVersion` (vertice-api's format `[A-Za-z0-9._-]{1,32}`, `consentVersionSchema` in `auth/schemas.ts`; any well-formed version, not only the current one; malformed → 400) and passes it to `CreateUser`. It is **required** (missing → 400, no upstream call); vertice-web-react sends it from the register form. `GET /auth/me` carries `consent` (`Consent` in `users/service.ts`, four nullable fields), read from `GetUser`'s self view. `POST /auth/me/consent` `{type: TERMS|HEALTH_DATA, version}` calls `RecordConsent` with the caller's own token and no user id: vertice-api takes the user from the token, so it is self-only by construction. The current versions come from env (`TERMS_VERSION`, `HEALTH_DATA_CONSENT_VERSION`, default `2026-10-draft`) through the public `GET /api/legal/versions` (`modules/legal`); the web compares them with `consent` to know when to ask again. Personal-data inventory and the (pending legal review) decisions: vertice-api's [`docs/data-inventory.md`](https://github.com/herbertpdl/vertice-api/blob/main/docs/data-inventory.md).

**Data-subject rights (P1-05):** the `/auth/me` routes are self only by construction (the user is the token's; no id in the request is read) and admit every role, ADMIN included. `GET /auth/me` returns `Me` with the CPF masked and no reveal (the user corrects it by typing a new one; the full value is in their export). `PATCH /auth/me` corrects the caller's profile through `UpdateUser` with their own token: omitted fields keep the stored value (read from the self view, since `UpdateUser` replaces everything), the stored role is always sent, a TRAINER's CPF can't be removed, a CREF is a TRAINER's only, a masked CPF is a 400; an email change has no verification yet (P1-06 follow-up). `DELETE /auth/me` `{password}` re-checks the password (`VerifyCredentials`, a wrong one is 400 `INVALID_CURRENT_PASSWORD`) before `DeleteAccount`, maps its FAILED_PRECONDITION (a TRAINER with active clients) to 409 `ACTIVE_CLIENTS`, answers 204, and the account's tokens are dead afterwards. `GET /auth/me/export` passes `ExportUserData`'s JSON through as an attachment (`vertice-dados-<date>.json`), 413 `TOO_LARGE` over vertice-api's bounds. Each writes an `audit: "account.update|delete|export"` log line (ids and field names only). A trainer's `DELETE /clients/:id` ends the relationship (`EndTrainerClientRelationship`), never the account; nothing in the BFF calls `DeleteUser`. vertice-api refuses deletes over a client's recorded history (plans, workouts, workout exercises, sets with logs) with FAILED_PRECONDITION, which reaches the client as 409 `PRECONDITION_FAILED` (`src/test/recorded-data.test.ts`). Spec: vertice-api's [`docs/specs/data-subject-rights/spec.md`](https://github.com/herbertpdl/vertice-api/blob/main/docs/specs/data-subject-rights/spec.md).

**Trust model:** the BFF is the first layer, vertice-api the authoritative one. The BFF checks roles and ownership so it can answer clients early and well, but vertice-api must authorize every call on its own from the forwarded identity (plan item P1-01). Every token the BFF mints is scoped `iss: "vertice-bff"`, `aud: "vertice-api"` with an `exp`, and the BFF verifies both on its own tokens too. User tokens carry only the identity (`sub` = the user id as a string, which vertice-api's `CallerIdentityResolver` reads) and `role`; `verifyToken` derives `req.user.id` from `sub`, and still accepts a token minted with the old numeric `id` claim only when it equals `sub` (such tokens expire within `JWT_EXPIRES_IN`). The API re-checks each user's stored role on every call; a deleted or demoted user gets 401 on their next request. The public auth routes call upstream with a short-lived service token instead (`sub: "service:bff"`, `role: "SERVICE"`, 60s, cached until 15s before expiry), which vertice-api allows on exactly `VerifyCredentials`, `CreateUser` and `SetPasswordWithToken`, and which `verifyToken` never accepts as a user. Ops scripts use their own `sub: "service:ops"` (allowed on `ListUsers` and `CreatePasswordSetupToken` only). Never widen either list for convenience: a service subject runs without a user, so whatever it may call, any bug on a public route may call too. Changing a claim's name, value or meaning is a cross-repo change: vertice-api validates it.

**Rate limits** (`src/plugins/rate-limit.ts`): `@fastify/rate-limit` provides a loose global per-IP bucket; the auth routes add strict buckets through `app.attemptLimit(name, {keys, count})` (an in-memory `AttemptLimiter`, `src/lib/attempt-limiter.ts`) that can refund an attempt once the response is known, so login/password setup count failures only and register counts every attempt. `DELETE /auth/me` has a bucket like `POST /auth/password` (IP + user, failures); `GET /auth/me/export` uses the `export` profile (`profile: 'export'`), its own limiter with `EXPORT_RATE_LIMIT_*` (3 per hour per user, every export counts), since one limiter's sweep needs one window length. Limits come from env (`AUTH_RATE_LIMIT_*`, `RATE_LIMIT_GLOBAL_*`) and `buildApp({ rateLimits })` overrides them in tests. Per-IP keys use `req.ip` (IPv6 cut to /64, `src/lib/client-ip.ts`); vertice-web-react calls the BFF server-side and forwards the browser IP as `X-Forwarded-For`, so deployed, `TRUST_PROXY` must name the web server or every web user shares one bucket. Every strict limiter also checks a per-network bucket (IPv6 /48, IPv4 /24, `AUTH_RATE_LIMIT_NETWORK_MAX`) before allocating keys; keys are fixed-size (email keys are a SHA-256 of the validated, normalized address). The `AttemptLimiter` sweeps expired buckets incrementally (bounded per call), deletes buckets refunded to zero, and is capped at `AUTH_RATE_LIMIT_MAX_KEYS`, failing closed (429) when full.

**Ownership/scoping** (`src/lib/ownership.ts`): beyond role checks, several resources need per-record ownership checks (a client can only touch their own plan; a trainer only their own client's). `assertOwnsPlan`, `assertOwnsWorkout`, `assertOwnsWorkoutExercise` walk up from a resource to its owning `TrainingPlan` and check `trainerId`/`clientId` against the requesting user (no ADMIN bypass). `assertOwnsWorkoutLog` loads the log (`GetWorkoutLog`): a CLIENT must be its `clientId`, anyone else goes through the plan of its workout. `assertCanUseExercises` resolves each body `exerciseId` a TRAINER puts into a workout through `GetExercise` with the forwarded token (vertice-api's workout-exercise writes don't check exercise visibility yet). Every route that takes an id must check it; `src/test/route-authorization.test.ts` holds one table entry per registered route (401 without a token, 403 for the wrong role, 403 for another tenant's id in path/query/body) against the in-memory upstream in `src/test/fakeUpstream.ts`, and fails when a new route has no entry. The **trainer↔client relationship itself** is not derivable from `User` or `TrainingPlan` — it's sourced from vertice-api's `TrainerClientService` (see `clients/service.ts`'s `assertIsTrainersClient`), which is the source of truth for "is this client one of this trainer's clients."

**Personal data (P1-03):** vertice-api returns users in a per-RPC view (self: every field plus the consent state, `GetUser` on the caller's own id; detail: every field but consent, to ADMIN or the active trainer; contact: id, name, role, email, on `ListUsers`/`CreateUser`/`VerifyCredentials`; summary: id, name, role, on `ListClientsForTrainer` and other lists), and the BFF narrows further. Never spread an upstream `User` into a response: build the shape field by field. `GET /clients` returns `ClientSummary` (no email, no CPF); the detail shapes (`ClientDetail` in `clients/service.ts`: `GET /clients/:id`, the overview's `student`, `PATCH`/`POST /clients`) carry the CPF masked (`maskCpf`, `src/lib/cpf.ts`), in full only on `GET /clients/:id?reveal=cpf`, which logs an `audit: "client.cpf.reveal"` line (actor and client ids, never the value); `/auth/me` is `Me` (CPF masked, no reveal). The CPF is optional for a CLIENT (`POST /clients` sends `''` when it is missing, which vertice-api stores as NULL) and required for a TRAINER. `UpdateUser` replaces every field, so `PATCH /clients/:id` without `cpf` reads the stored CPF (`GetUser`) and sends it back; only `cpf: null` removes it. A masked CPF (contains `*`) is a 400 on both routes, so the mask is never stored as a CPF. `ListUsers` is paginated (at most 100 per page): go through `userPages`/`listAllUsers`, never a single `listUsersPage` call when you need everyone.

**Composed/aggregate endpoints:** several routes exist specifically to save the frontend from orchestrating multiple calls — `GET /clients` (roster with plan/activity enrichment), `GET /clients/:id/overview` (client-detail header stats incl. an approximated 4-week adherence %), `GET /workouts/:id/full`, `GET /workouts/:workoutId/session` (auto-starts/resumes the week's log and merges in last-performed set values), and `GET /dashboard`. These exist because vertice-api's gRPC surface is narrow (e.g. `ListWorkoutLogs` is scoped to one `trainingPlanId` + one `weekStartDate` — there's no general history query), so service functions often approximate or re-fetch across a small date window rather than there being a matching upstream RPC. When touching these, read the surrounding comments in the service file first — they document exactly which upstream limitation is being worked around and why the approximation is shaped the way it is.

**Error handling:** all errors are `HttpError` subclasses (`src/lib/errors.ts`: `NotFoundError`, `ConflictError`, `UnauthorizedError`, `ForbiddenError`, `ValidationError`, `PreconditionFailedError`, `TooManyRequestsError`), thrown from anywhere (routes or services) and caught by the global handler (`src/plugins/error-handler.ts`), which also maps `ZodError` and Fastify's own validation errors to the same `{ error: { code, message, details } }` shape. Don't `reply.send()` an error response manually — throw instead.

**Config** (`src/config/env.ts`): all env vars are parsed once through a Zod schema at import time (`env`); there's no other place reading `process.env` directly for app config (use `env.NODE_ENV`, which is trimmed and lower-cased). `grpcTarget` is derived here too.

## Current module layout

`auth` (also `/auth/me` PATCH/DELETE, `/auth/me/export`, `/auth/me/consent`), `legal` (`GET /legal/versions`, no upstream call), `clients` (trainer's roster of CLIENT users — recently replaced a `students` module; sourced via `TrainerClientService`, not derived from training plans), `dashboard`, `exercises` (also owns `/muscle-groups`), `exercise-sets`, `training-plans`, `users` (shared `User` type/mapping and `UserService` wrappers, no own routes), `workouts`, `workout-exercises`, `workout-sessions` (also owns `/workout-logs` and `/workout-sessions/:id/{sets,complete}`), `feedback`.

## Reference docs

Feature-level changes to the REST surface get a spec under `docs/specs/<feature-slug>/spec.md`
(same slug as the matching `vertice-api` PRD/spec) describing which endpoints are exposed and how
they map onto upstream RPCs — see `docs/specs/create-workout-with-exercises/spec.md`. Cross-repo
references in docs are GitHub links (`https://github.com/herbertpdl/<repo>/blob/main/<path>`),
not `../<repo>/...` relative paths; same-repo references stay relative.

Every spec that touches more than one repo has a **"Merge and deploy order"** section listing
the repos in the order their PRs merge and deploy, and why (which side needs the other already
live). The default is `vertice-api` → `vertice-bff` → `vertice-web-react` / `vertice-mobile`:
the API adds RPCs before the BFF calls them, and the BFF exposes endpoints before a client
uses them. State any deviation explicitly (e.g. a removal goes clients first, API last), plus
the rollback order.


`docs/api-contract.md` documents the full REST surface (request/response shapes, role requirements, and the same upstream-limitation notes as the code comments) and is generally reliable for endpoint-level detail — but it predates the `students`→`clients` rename and still refers to a `/students` route; treat anything mentioning `/students` there as referring to what is now `/clients`.
